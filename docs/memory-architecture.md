# Архитектура памяти

Главная ошибка — считать «памятью» что-то одно. Здесь три разных механизма
с разными свойствами, и путать их нельзя.

## 1. Полный журнал (append-only)

**Что:** каждое сообщение, вызов инструмента, файл, вердикт гейта.
**Где:** `~/.academic/journal/YYYY-MM.jsonl`.
**Свойство:** неизменяемость с доказательством (hash-chain).
**Зачем:** вопрос «что именно обсуждалось и почему решили так» должен иметь
ответ, который нельзя переписать.

Подробности: [journal-format.md](journal-format.md).

## 2. Реестры (структурированная, редактируемая память)

**Что:** `evidence`, `claims`, `decisions`, `gates`.
**Где:** SQLite (`~/.academic/journal.db`), экспорт в CSV/Markdown.
**Свойство:** редактируется человеком; каждый объект имеет идентификатор.
**Зачем:** то, что нужно *вести*, а не хранить: статус проверки утверждения,
условие пересмотра решения, вердикт гейта.

Именно реестры отвечают на вопрос «чтобы не возвращаться к уже решённому»:
`decisions.status = active` с полем `reopen_if`.

## 3. Семантическая память (производная)

**Что:** решения, ограничения, уроки, предпочтения, терминология проекта.
**Инструменты:** `Gentleman-Programming/engram` (6.7k★, MIT, Go-бинарь,
SQLite+FTS5, MCP/CLI/TUI) или `rohitg00/agentmemory` (28.6k★, Apache-2.0,
широкий охват агентов).
**Свойство:** перезаписываемая, приблизительная, всегда со ссылкой `journal_id`.
**Зачем:** быстро находить «а что мы решили по поводу X» без чтения журнала.

## Почему саммари не заменяет журнал

| | Журнал | Семантическая память |
|---|---|---|
| Полнота | 100% событий | выжимка |
| Доказуемость | хеш-цепочка | нет |
| Потеря нюанса | нет | всегда |
| Восстановление | невозможно после удаления | пересобирается из журнала |
| Стоимость | дешёвая запись | дорогое извлечение |

Практическое следствие: **если что-то записано только в памяти, считайте, что
этого нет.** Правило для агента: каждая запись памяти получает `journal_id`,
иначе она не имеет силы.

## Консолидация (конец сессии)

```
журнал за день ──► извлечение кандидатов ──► реестры ──► память
                    (решения, уроки,            (decisions,     (Engram/
                     ограничения, вопросы)       claims)          agentmemory)
```

Ограничение: 3–7 новых пунктов за сессию. Больше — значит вы пишете
пересказ, а не память.

## Что НЕ нужно помнить

- полный текст обсуждений (он в журнале);
- промежуточные версии файлов (это git + хеши в журнале);
- всё подряд «на всякий случай» (мусор в памяти снижает точность поиска).

## Выбор инструмента

| Сценарий | Рекомендация |
|---|---|
| Один исследователь, локально, нужен MCP и поиск | **Engram**: один бинарь, SQLite+FTS5, CLI/TUI, MIT |
| Много агентов (Claude, Codex, Cursor, Copilot, Gemini CLI) | **agentmemory**: готовые плагины под каждый агент, Apache-2.0 |
| Нужен сервер с несколькими пользователями | `chirino/memory-service` — **только как эксперимент**: автор прямо пишет «proof of concept» |
| Вообще ничего не ставить | SQLite-реестры + `journal.search` этого репозитория закрывают 80% потребности |

## Практика «не возвращаться к решённому»

1. Решение фиксируется в `decisions` с полем `reopen_if` — условием, при котором
   вопрос открывается снова.
2. `make resume` показывает активные решения первым блоком.
3. Пока условие не выполнено, обсуждение не возобновляется.
4. Если возобновилось — сначала запишите, какое условие сработало, потом спорьте.

Это единственный надёжный способ не тратить сессии на одни и те же споры:
не «умная память», а явное условие пересмотра.
