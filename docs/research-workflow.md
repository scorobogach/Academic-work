# Рабочий процесс исследования

Репозиторий не диктует методологию, а задаёт точки контроля. Ниже — схема,
совместимая с `Imbad0202/academic-research-skills` (ARS) и с ручной работой.

## Стадии и артефакты

| Стадия | Артефакт | Что пишется в журнал | Гейт |
|---|---|---|---|
| 0. План | `templates/research-plan.md` | `decision` (вопрос, дизайн, критерии) | — |
| 1. Протокол | предрегистрация / registered report | `decision`, `file` (hash протокола) | — |
| 2. Поиск литературы | `templates/evidence-ledger.csv` | `evidence` на каждый источник | — |
| 3. Данные и код | `analysis/`, `data/raw/` | `file` (хеши), `decision` (обработка) | G6 |
| 4. Анализ | `analysis/results.json`, таблицы, фигуры | `note`, `tool_result` | G5, G6 |
| 5. Черновик | `manuscript/*.tex` | `message`, `file` | G0, G1 |
| 6. Проверка утверждений | `templates/claim-audit.md` | `claim` | G3, G4 |
| 7. Правка | версия 2 | `message` | G2, G0, G1 |
| 8. Рецензия | отзыв рецензента | `note`, `decision` | — |
| 9. Ответ рецензенту | `templates/response-to-reviewers.md` | `decision` | G2 |
| 10. Сдача | disclosure + подпись | `signoff` | G7 |

Правило перехода: **следующая стадия не начинается, пока блокирующие гейты
текущей не зелёные**, либо расхождение не зафиксировано как осознанное
исключение в `decisions` (с обоснованием и условием пересмотра).

## Как сочетать с ARS

ARS ведёт сами стадии (исследование → написание → рецензия → правка → финализация)
и содержит собственные integrity-гейты. Разделение ответственности:

| Задача | Кто |
|---|---|
| Стадии, режимы, рецензирование | ARS |
| Поиск и проверка литературы | CiteCheck / ARS / OpenAlex MCP |
| **Неизменяемый журнал всего процесса** | этот репозиторий |
| Реестры claims/evidence/decisions | этот репозиторий |
| Детерминированные гейты G0 G1 G3 G5 | этот репозиторий |
| Контекст-пак между сессиями | этот репозиторий (`resume`) |

Практика: на каждом переходе ARS делайте `journal.append` с типом `gate_run`
или `note` и идентификатором стадии. Тогда «что происходило» восстановимо
независимо от того, остался ли ARS в вашем наборе инструментов через год.

## Ежедневный цикл (15 минут)

```
1. make resume                       # что решено, что блокирует, что делать
2. работа                            # утверждения → claims, источники → evidence
3. make gates                        # G0 G1 G3 G5 по изменённым файлам
4. решения → decisions.upsert        # с reopen_if
5. make journal-verify               # цепочка цела
```

## Еженедельный цикл (1 час)

```
1. make reproduce                    # пересборка таблиц из сырых данных
2. export реестров → CSV/Markdown     # вложение в рукопись
3. сверка G4 по выборке утверждений  # не все сразу: 10–15 за раз
4. бэкап: копия journal/ + journal.db на второй носитель
```

## Перед сдачей (чек-лист)

- [ ] `make gates` — все блокирующие зелёные; исключения оформлены в `decisions`
- [ ] G4: у каждого фактического утверждения есть `source_id` + локатор + `supported`
- [ ] G5: все числа трассируются на `results.json`; `blocking` включён
- [ ] G6: `make reproduce` воспроизводит таблицы и фигуры; манифест данных совпадает
- [ ] G7: лог ИИ по секциям, disclosure, конфликт интересов, `SIGN-OFF.md`
- [ ] `make journal-verify` — цепочка цела; `MANIFEST.sha256` зафиксирован
- [ ] бэкап журнала и БД — минимум две копии
- [ ] canary-тест контура проведён в этом месяце и его recall ≥ 0.8
