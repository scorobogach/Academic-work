# Выбор хранилища: почему SQLite, а не PostgreSQL

Решение принято за вас (вы просили решить самостоятельно). Ниже — обоснование,
чтобы решение можно было оспорить.

## Требования, из которых исходило решение

1. **Один исследователь, одна машина, офлайн.** Научная работа часто идёт в
   поездках, без сети и без прав администратора.
2. **Срок жизни — годы.** Работа должна открыться в день, когда рецензент
   спросит: «а что именно обсуждалось 14 марта?»
3. **Доказуемость.** Нужно показать, что журнал не менялся.
4. **Нулевая стоимость владения.** Никакого демона, контейнера, миграций.
5. **Полнотекстовый поиск по-русски** из коробки.

## Сравнение

| Критерий | SQLite (+FTS5) | PostgreSQL (+pg_trgm / tsvector) |
|---|---|---|
| Установка | нет (встроен в Python) | нужен сервер, пользователь, БД |
| Работа офлайн | да | только если сервер локальный |
| Бэкап | копирование одного файла | `pg_dump` + расписание |
| Полнотекстовый поиск | FTS5 с `unicode61` — кириллица из коробки | нужен `to_tsvector('russian')` и настройка |
| Совместный доступ | один писатель (WAL снимает часть ограничений) | несколько писателей |
| Риск «не поднимется через год» | минимальный | средний (версия сервера, расширения) |
| Масштаб | до десятков ГБ и миллионов записей | больше |

Для одиночной научной работы SQLite выигрывает по всем пунктам, кроме совместного
доступа. Диалог/journal — это_append-only_ последовательность: одновременная запись
не нужна, а чтение из нескольких процессов SQLite умеет.

## Когда всё-таки PostgreSQL

- работа в группе: несколько человек пишут в один журнал проекта;
- журнал используется как сервис для нескольких агентов одновременно;
- уже есть администрируемый сервер и резервное копирование;
- нужен полнотекстовый поиск по очень большому архиву (сотни ГБ).

## Как перейти, не переписывая код

Слой доступа изолирован в `scripts/academic_journal/db.py`. Переход выглядит так:

1. Схема переносится почти как есть: `TEXT` → `TEXT`, `INTEGER` → `INTEGER`,
   `REAL` → `DOUBLE PRECISION`, автоинкремент — `BIGSERIAL`.
2. Полнотекстовый поиск: FTS5 заменяется на `to_tsvector('russian', ...)`
   + GIN-индекс; запрос `MATCH ?` — на `plainto_tsquery('russian', ?)`.
3. DSN задаётся переменной `ACADEMIC_DB`:
   `sqlite:///~/.academic/journal.db` или `postgresql://user:pass@host/db`.
4. Журнал (`journal/*.jsonl`) не меняется вообще — это файлы, а не БД.

Обратная совместимость: экспорт реестров в CSV/Markdown сделайте **до** миграции,
это независимый от СУБД слепок.

## Что точно не надо делать

- Хранить БД или журнал внутри git-репозитория рукописи. Бинарный файл в истории
  растёт, `.db-wal` попадает в коммиты, а содержимое (персональные данные) —
  в облако. Каталоги уже внесены в [.gitignore](../.gitignore).
- Держать единственную копию. Правило 3-2-1: рабочая копия, локальная резервная,
  внешняя. Журнал — единственный невосстановимый артефакт.
- Использовать облачную синхронизацию (Dropbox/Drive) напрямую на файл `.db`:
  concurrent-запись ломает базу. Синхронизируйте **копии** по расписанию.
